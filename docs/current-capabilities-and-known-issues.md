# 当前能力与已知执行问题

记录日期：2026-10-15。本文区分已实现功能、验证证据和未实现方案。

## 已具备的功能

- Electron + React 桌面工作区：游戏窗口选择、实时预览、PNG/JPEG 导入、模型连接配置、任务对话、Trace 和模拟 MCP 诊断。
- Pi Agent Core 统一模型与工具循环；支持 OpenAI 兼容的图片输入、工具调用和流式输出。依赖 Node >=24.20.0 和固定版本的同级 Pi 源码，详见 README。
- 意图分流：chat 普通聊天，observe 只读视觉观察，act 执行任务，clarify 澄清。分类阶段不授予游戏工具；无效输出和低置信度不执行动作。保留最近 12 条文本消息，重启后清空。
- 导入图片可进入观察请求；聊天分类知道当前图片来源与可用视觉能力。模型可获知当前模式的工具名称、参数和限制，询问工具清单不会触发输入。
- 三种输入模式：内存模拟手柄 MCP、Windows SendInput 真实键盘、Python vgamepad + ViGEmBus 真实 Xbox 360 XInput 手柄。独立 MCP 服务和诊断面板仍为模拟后端。
- 真实闭环：理解指令 → capture_game 新帧 → 规划 → keyboard_action / gamepad_action → 释放输入 → 新截图回传 → 模型反馈。真实手柄支持双摇杆、双扳机与按键组合，任务自动连接，也可提前手动连接供 Cemu 配置。
- 动作限制为每次 20–1000 ms、最多 4 次动作、12 次工具调用、10 轮模型决策；有总超时、取消、窗口身份和焦点检查、输入释放及应用退出清理。
- Trace 与运行落盘：顺序事件、输入和过程截图、manifest、summary；日志脱敏且不写入图片 Base64。control_passed 表示真实输入反馈链路通过，gameOutcome 仍为 unverified。
- 清理未引用 UI、旧实验/验收编排与 Web 沙盒，统一 Session、Recorder 与 Pi 执行入口，保留历史 Trace 展示所需类型。

## 使用与验证边界

- 模型 API 面板保存的是内存覆盖配置，应用重启后需要从环境变量或配置文件重新加载；默认配置位于同级 Pi 的 .pi-agent/models.json，不随本仓库提交。JSON 字符串内的原始制表符/换行会导致解析失败。
- Cemu 首次使用需在输入设置载入/保存配置并关联实际连接的 XInput 设备；配置档存在不代表设备在线。Xbox 接口不提供陀螺仪输入。
- 已有自动测试覆盖意图路由、图片传递、工具参数、Session、MCP、日志与 UI。运行时测试采用本地脚本模型，不衡量线上模型智能或分类准确率。
- 本机此前的 artifacts/virtual-gamepad-check.json 记录 XInputGetState 实际读到手柄按键/轴报告，并验证释放、取消归零、最小化阻止输入、失焦释放。
- 本机此前的 artifacts/gamepad-loop-check.json 记录完整闭环：4 次本地模型请求、3 张回传图片、control_passed。该脚本中的 cancelReleased / unfocusedInputBlocked 为 false 表示手柄分支未执行键盘专属检查；手柄取消和失焦由独立 virtual-gamepad 测试覆盖。
- 用户在 Cemu 实际游戏中确认能够按任务移动和执行动作；这不等于已经验证复杂任务成功率。运行记录及截图保留本地，不纳入仓库。

## 未解决：接近目标时错过短暂交互提示

### 现场与复现条件

用户在 Cemu 1.26.2f 的《塞尔达传说：旷野之息》复苏神庙场景，要求：“操控林克向发蓝光的神庙交互装置移动，直到出现交互按键，中途需要控制林克跳跃一次”。

用户报告移动途中已出现交互按键，但随后动作继续移动并走过交互范围。截图中的模型总结声称已经移动、跳跃，但未确认交互提示；可见工具参数包含 left_x=0.35、left_y=0.7、duration_ms=400。该截图不能独立证明所有动作、提示出现时间或跳跃结果，尚未依据完整运行记录确定根因。

### 已确认的实现事实

1. game-loop.ts 先等待完整动作结束，再调用 host.capture；没有执行期间的视觉提示检测与提前停止。
2. virtual-gamepad.py 在动作中检查取消和窗口状态，并最终归零，但没有读取游戏画面或检测交互提示。
3. 模型思考期间上一动作已经释放；游戏仍运行，惯性、动画、敌人和环境可以继续变化。
4. 捕获有源帧屏障校验，但它只保证请求的新帧，不保证捕获到两个观察点之间出现又消失的提示，也不保证模型读懂提示。

因此可能原因包括动作步长过长、采样间隙漏掉瞬时提示、模型漏识别或下一步规划过大；“截图耗时太长”目前是待验证假设。

### 建议改造（尚未实现）

- 靠近目标时减小摇杆幅度和动作时长，80–150 ms 可作为调试起点；总时间与无进展停止条件配合更合理的动作预算，避免细步移动被当前 4 次上限截断。
- 动作期间缓存画面并保留触发关键帧；中间帧用于复盘，不能单独替代实时停止。
- 增加本地快速视觉监测：针对交互区域进行图标匹配/OCR，区分常驻移动教程与真正交互提示。15–30 FPS 为待测目标，不是当前性能承诺。
- 增加带停止条件的 move_until 一类工具：检测到目标提示立即归零、取消剩余移动，回传停止原因、实际时长、触发截图和停止后截图供模型复核；超时或检测失效也释放输入。
- 执行下一步前检查最新交互状态，避免基于过时状态继续移动；用户只要求出现提示时应停下，不自动按交互键。
- 记录采集、检测、模型响应和输入释放时间，评估端到端停止延迟。

### 后续验收

- 在受控窗口中让交互提示仅在一次移动中途短暂出现，验证检测后剩余动作被中断，输入实际归零，并保留触发画面。
- 覆盖无提示超时、错误/相似提示、检测失效、失焦、取消和模型慢响应；确认慢响应期间输入中立。
- 再在 Cemu 重复接近装置任务，报告提示捕获率、停止延迟、越过目标次数与任务成功率，不以工具调用成功代替游戏目标完成。
